# Human-First Quality Review

## Правила аудита

- `audit` = read-only; нельзя менять Figma/код/данные под видом аудита.
- Сначала изучи существующие дизайн-системы и зафиксированные требования.
- Разделяй **наблюдаемое**, **вероятное** и **непроверенное**.
- У каждой значимой находки должны быть: конкретный экран/узел или строка,
  evidence, причина, impact и исправление. Не «UI выглядит устаревшим».
- Не утверждай «проверено в браузере», если видел только статичную картинку.
- Для серьёзной работы требуется минимум одна повторная итерация после
  визуальной проверки. Формат — не самоцель, а рабочий цикл качества.

## 7 критериев качества (0–4)

| Критерий | Что измеряем |
|---|---|
| 1. Task clarity | цель, иерархия, предсказуемые действия |
| 2. Brand & visual | стиль из предметной области, читаемость, ритм, anti-slop |
| 3. System integrity | reuse, tokens, variants, структура, отсутствие drift |
| 4. Interaction | поведение controls, feedback, states, отмена |
| 5. Trust & AI (если AI) | границы, evidence, control, recovery, autonomy |
| 6. Accessibility & i18n | keyboard, контраст, reduced motion, русский, responsive |
| 7. Production readiness | реальные данные, производительность, ошибки, безопасные права |

**Оценка:** 0 = отсутствует/сломано; 1 = серьёзно нарушено; 2 = терпимо,
но есть проблемы; 3 = хорошо; 4 = образцово для контекста.

Не выставляй искусственные десятые доли. Сумма — ориентир, а не замена
разбора. Если критерий неприменим (AI на статическом не-AI сайте), пометь
`N/A`; не занижай общий балл за отсутствие ненужной AI-фичи.

## Severity

- **Critical:** неверные права/утечка данных, необратимое действие без
  защиты, опасная ошибка, невозможность завершить главное действие.
- **High:** потеря данных, нерабочий ключевой сценарий, ложный статус успеха,
  значимое перекрытие, недоступность управления или неподтверждённые источники
  в критическом AI-выводе.
- **Medium:** ломается responsive/i18n, системный дрейф, неполная ошибка,
  неудобная проверка источника, нарушенная типографика.
- **Low:** локальный ритм, второстепенное выравнивание, несущественный
  декоративный шум без ущерба по функции.

## Пятислойный QA

### 1. Content
- Тексты согласованы и не придуманы, реальные примеры.
- RU грамотный, бренд/имена не переведены случайно.
- Нет висячих коротких предлогов, визуальной «каши» и лишних CTA.

### 2. Visual
- Выраженное главное действие; читаемая типографическая шкала.
- Нет механической одинаковости секций без причин.
- spacing/radius/icons совпадают с системой; state colors семантичны.
- Выравнивание левых краёв заголовков, полей, колонок, таблиц и footer.

### 3. Interaction & states
- Отдельно изучены hover/focus/active/loading/empty/error/disabled.
- Удаление и отмена подписки/действия имеют понятный confirm/recovery.
- Нет мёртвых кнопок, бесконечных загрузок или toast не про то действие.

### 4. Responsive & accessibility
- Desktop, mobile, tablet; длинная строка, chips overflow, sticky.
- Keyboard navigation, input label, focus visible, zoom 200%, контраст.
- Reduced motion, предпочтения OS, валидные target sizes.

### 5. AI reliability (если есть)
- Отличено AI от deterministic.
- Evidence открывается; подсказки не отвлекают; можно reject/regenerate/edit.
- Есть пути error/uncertainty/handoff; автономность соразмерна риску.
- Trust boundary для входных документов и privacy third parties.

## Browser repair loop

Для новых публичных сайтов и B2B-экранов применяй `references/taste-v2-process.md`: 3
ширины, до 3 крупнейших подтверждённых дефектов за итерацию, повторная
проверка изменений. Для AI-поверхностей подключи
`references/ai-test-cases.md`, а результаты заноси в `templates/qa-report.md`.

## Скриншотный цикл

1. Получи screenshot или реальный preview исходного состояния.
2. Сопоставь с референсом **этого** бренда/сценария.
3. Найди три крупнейших дефекта (или меньше, если их меньше).
4. Исправь первопричину, не поверхностную косметику.
5. Перепроверь затронутые breakpoint + соседние состояния.
6. Повтори, если остались Critical/High и фундаментальные визуальные дефекты.

Если среды выполнения нет, напиши «нуждается в визуальной проверке», а не
«проверено и отлично».

## Anti-sycophancy review

Проверь, не согласился ли ты с неверным исходным тезисом: например,
«добавить доверие» не означает «добавить бейдж 98%», «сделать богаче»
не означает «залить все секции градиентом», «оптимизировать» не означает
«убрать из AI-сценария approval». Когда споришь, предложи замену и критерий
успеха, а не просто субъективную оценку вкуса.
