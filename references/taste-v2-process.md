# Taste v2.x / Frontend Design: art direction → implementation → inspection

Это **самостоятельная операционализация**, а не перепечатка чужих skills.
Taste Skill v2.x описывает 6 этапов: client-specific brief → выбор направления
→ привязка идеи к предметной области → реальные изображения → реальный браузер
на 3 ширинах → исправление трёх крупнейших проблем (до 3 кругов). Для
app/dashboard у Taste Skill v2.1 отдельный маршрут. В `human-first-design`
используй этот принцип, не копируя чужой алгоритм случайной раздачи стилей.

## 1. Предметная опора

Ответь прежде, чем выбирать шрифты:
- Что человек узнаёт на этом экране за первые 5 секунд?
- Какие реальные объекты, материалы, форматы, единицы измерения и рабочие
  привычки отличают данную сферу от других?
- Какую эмоцию/уровень строгости бренд уже согласовал?
- Какая **настоящая** визуальная сущность является носителем идентичности?
- Какой шаблон AI-генерации почти наверняка даст безликий результат?

Нельзя считать «премиально», «минимализм» и «современно» самостоятельной
арт-дирекцией. Нужна связь решения с предметом и аудиторией.

## 2. Для новых marketing-сайтов: две авторские альтернативы

Выработай два направления из контента (не из случайного style picker):

| Параметр | Что фиксируем |
|---|---|
| Character | 2–3 конкретных прилагательных, отражающих предмет |
| Hero | Конкретный предмет/демо/заголовок как ведущий носитель |
| Layout | Ширина, сетка, асимметрия, ритм секций и точка первого CTA |
| Type | Семейство или свойства, кириллица, веса, line length |
| Color | 4–6 семантических цветов либо подтверждённые brand tokens |
| Media | Реальные фото/схемы; источник, право использования, alt |
| Motion | Один функциональный приём, не сборник переходов |
| Anti-template | Какие два типовых решения сознательно не применяем |

Выбери направление, которое легче защищать содержательно; дальнейшая
реализация не должна превращаться в гибрид обоих вариантов.

**Визуальные фотографии/видео:** при отсутствии клиентских материалов ищи
правомерно доступные ассеты (public domain/CC0/подходящая CC), записывай
автора, название, URL, лицензию, требуемую атрибуцию. Не используй
watermarked изображения, слепые «Google картинки» и недоказанные права.
Не ставь сгенерированное изображение на место реального продукта без
согласования и маркировки.

## 3. Для B2B-продуктов: функциональная арт-дирекция

Принцип Taste v2.1: у app/dashboard свой путь, отличный от landing. Не
воспроизводи случайный shell другой SaaS. Привяжи дизайн к реальным данным:
- Определи информационную архитектуру: global nav, context, primary action,
  workspace, details, table/filter, statuses, bulk actions, footer/pagination.
- Сохрани известные ширины sidebar и column contracts, проверь sticky.
- Заголовок и функция страницы узнаваемы на первом экране.
- Денежные суммы/единицы/периоды выровнены и форматированы согласованно.
- Цвет трать на данные/статусы, не на декоративные поверхности.
- Таблица остаётся таблицей на desktop; на mobile выбери meaningful
  приоритет полей или горизонтальный скролл с явной доступностью.
- Для аналитики график обязан отвечать на вопрос, иметь реальную ось,
  единицы и доступную текстовую альтернативу.

Продукт с утверждённым kit не получает альтернативную палитру и «уникальный
шрифт» по совету скилла. Вкус здесь проявляется в ясной структуре и polish.

## 4. Browser-based repair loop

**Нельзя считать код просмотром.** Действия зависят от доступных инструментов:

1. Получи реальную страницу/скриншот. Запиши URL/фрейм и время или версию.
2. Сделай состояния на минимум 3 ширинах: `390`, `820`, `1440` CSS px;
   при редакторе проверь релевантные Figma breakpoints.
3. Смотри визуально: не просто DOM/accessibility snapshot. Назови до 3
   подтверждённых дефектов и причину каждого.
4. Исправь в порядке: функциональный блокер → информационная иерархия →
   overflow/alignment → типографика → вторичная графика.
5. Перепроверь **изменённые** breakpoint, hover/focus, RU/EN, error/empty;
   не вводи регрессии в уже подтверждённое.
6. Повтори до чистого состояния или максимум 3 цикла; не маскируй остаточные
   серьёзные проблемы фразой «всё отлично».

Если браузера/превью нет, помечай `Not tested`, не `Pass`. Процесс никогда
не требует установки браузера или npm зависимостей без разрешения и задачи.

## 5. Preflight — стопы против генеративных шаблонов

Пройти по каждому экрану/сайту:
- Не мог бы этот hero принадлежать десяти другим компаниям без замены текста?
- Есть ли типичная схема centered headline → gradient pill → 3 clones?
- Не заменили ли реальное изображение абстрактным blob без причины?
- Каждый eyebrow label / numbered marker / italic accent несёт смысл?
- Не повторяется ли одинаковый hover-scale / fade-up на всём сайте?
- Визуальная плотность согласуется с задачей (данные vs storytelling)?
- В шрифте и сетке отражается бренд, а не личная привычка агента?
- Реальный первый экран показывает продукт/услугу/действие без скролла?

Отдельный запрет: **anti-slop сам не должен стать эстетическим шаблоном**.
Тёмно-серый + кислотный акцент, кремовый + антиква, газета с разделителями —
такие же готовые стили, если не обоснованы предметом.

## 6. Границы применения

`DESIGN_VARIANCE`, `MOTION_INTENSITY`, `VISUAL_DENSITY` — ручки прошлых
версий Taste Skill, а не обязательный механизм актуальной v2. Они пригодны
для обсуждения степени смелости/движения/плотности, но **не заменяют**
конкретное направление и проверку в браузере.

Источники: `references/sources.md`. Не представлять этот документ как
«официальный Taste Skill» и не обещать идентичные скрипты или выбор стилей.
